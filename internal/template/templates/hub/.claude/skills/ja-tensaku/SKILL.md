# 日本語添削（ja-tensaku）

## これは何をするか

書かれた日本語を、意味を変えずに「自然で読みやすい日本語」に直す。とくに、英語や機械翻訳から来る硬さを取り除く。
エージェントが自分の返信やノートを送る前に自己チェックする用途も想定する。

## なぜ必要か

エージェントの日本語は、放っておくと翻訳調になりやすい。原因は、英語の発想のまま語を置き換える／専門語をカタカナで済ませる／
要点を体言止めで並べる／修飾を一文に詰め込む、といった癖だ。一つ一つは小さいが、積もると「意味は分かるが、日本語を母語とする人が
書いた文章には見えない」状態になる。読み手の負荷が上がり、中身より文体に気を取られてしまう。だから、送る前にこの癖を潰す。

## 直す 6 つの癖（悪い例 → 良い例）

### 1. 翻訳調・直訳

英語の構文をそのまま日本語に移すと不自然になる。主語の多用、無生物主語、「〜することができる」「〜という事実」が典型。
- 悪: この変更はビルド時間を短縮することができる。
- 良: この変更でビルドが速くなる。
- 悪: テストが落ちているという事実が重要だ。
- 良: テストが落ちているのが大事だ。

### 2. カタカナ語の乱用

専門語を英語カナのまま並べると、内輪の符丁になって読みにくい。日本語で言えるものは日本語にする（十分に定着した語は残してよい）。
- 悪: レイテンシのボトルネックはリトライのタイムアウトでリカバーされる。
- 良: 遅さの原因は、再試行の待ち時間を見直せば解消する。
- 残してよい例: ログ、キャッシュ、コミット（定着済み）。

### 3. 体言止めの多用

要点を名詞で切って並べると、メモにはなるが文章にならない。述語を戻す。
- 悪: 遅い原因はディスク I/O。直す主な手はキャッシュ。
- 良: 遅い原因はディスクの読み書きだ。それを直す一番の手はキャッシュになる。

### 4. 一文が長すぎる

修飾・並列・逆接を一文に詰めると、読み手が息継ぎできない。文を割る。
- 悪: メモリは足りているが CPU が張り付いており、しかも夜間バッチだけが遅くて他は先月と同じ時間で終わっている。
- 良: メモリは足りている。問題は CPU だ。遅いのは夜間バッチだけで、ほかは先月と同じ時間で終わっている。

### 5. 常体と口語の混在でトーンがブレる

「〜だ／である」と「〜だよ／〜してくれんか」が混ざると、誰が喋っているのか分からなくなる。相手と場面に合わせて一つに寄せる。
- 悪: 判定は延期だ。だから今日できるのは計測値をメモっておくところまでなんだよね。
- 良: 判定は延期。だから今日は計測値をメモするところまでにする。

### 6. 記号（——／＝／・）の多用

ダッシュ・イコール・中黒で概念を圧縮すると、図解メモのようになって文章の流れが切れる。接続詞や述語に開く。
- 悪: 含意＝設定変更は主な手にならない兆候・重心はコード側へ。
- 良: つまり、設定の変更は主役になりにくい。力を入れる先はコード側に移す。

## 進め方

1. まず全文を読み、言いたいことを取る。添削で意味を変えない。
2. 上の 6 観点で、直す箇所を「引用 → なぜ不自然か → 直し」の 3 点で挙げる。数が多いときは、効果の大きい順に絞る。
3. 最後に、直しを反映した**クリーン版の全文**を出す。読み手はこれをそのまま使える。
4. 迷ったら「声に出して読んで、詰まるか」で判断する。詰まる所が直す所だ。

## 自己添削として使うとき

エージェントが日本語でまとまった返信やノートを書いたら、送る前にこのスキルを通す。とくにカタカナ語と記号は自分では気づきにくいので、
重点的に見る。指摘の列挙は省いてよいが、クリーン版には必ず落とす。相手が砕けた口調なら、無理に硬くせず、その口調のまま自然に整える
（丁寧語へ勝手に変えない）。スキル `research-distill` の手順 4（蒸留）では、`braindex answer` で HTML にする前にここを通す。
