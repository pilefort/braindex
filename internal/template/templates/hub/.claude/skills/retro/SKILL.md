# レトロスペクティブ（訂正率トリガ）

計測（訂正率）は `braindex retro` が決定論で済ませる。ここで行うのは判断: 訂正の中身を読んで型を見つけ、規約の直し方を提案すること。
セッションログの本文は OS の一時ディレクトリにしか置かず、リポには残さない。リポに残すのは数値と所見だけ。

1. 材料を出す。hub のルートで `braindex retro extract -window-days 14` を実行する（窓は `braindex.json` の `retro.window_days` と、
   `check` が知らせた期間に合わせる）。要約行に出力先（一時ディレクトリの `braindex-retro`）が出る。
   `index.tsv` に、セッションごとの開始日時・プロジェクト・セッション ID・発話数・訂正数・ダイジェストのパスが並ぶ。
2. 読む。`index.tsv` を訂正数の多い順に見て、ダイジェスト（`sessions/<プロジェクト>/<開始日時>_<ID>.md`）を読む。
   見出しの ★ は訂正辞書に当たっただけの候補で、訂正かどうかは前後（`← ASSISTANT` の本文と、その前の発話）を読んで判断する。
   ★ の無い発話にも訂正はある（辞書は定型句しか拾わない）。☆ は感情辞書（感謝・不満）に当たった候補で、C の手がかりにする（率には入らない）。
   セッションが多ければ（目安: 30 を超える）、プロジェクトか `index.tsv` の行の範囲ごとにサブエージェントへ委任し、
   下の 3 分類で 30 行以内に報告させる。委任にはダイジェストのパスと 3 分類の定義を渡し、本文の転記は 1 行以内と指示する。
3. 所見を 3 分類で列挙する。各項目に発話の日時（ダイジェストの `[MM-DD HH:MM]`）・プロジェクト・要約を付ける。本文の転記は最小限（1 行以内）。
   - **A 訂正の型**: 何を直されたか（意図の取り違え／規約があるのに効いていない／頼まれていない拡張／出力の形式 など）。同じ型が何回出たか
   - **B 繰り返し指示**: 同じ指示が別のセッションで何度も出ている（規約に無い、または規約が効いていない印）
   - **C うまくいった協働**: 感謝や承認で終わった流れ。何が効いたか（修正だけでなく成功も規約に残す）
4. 規約への反映案を出す。A・B の型ごとに、CLAUDE.md か rules のどこに何を足す／直すかを 1 行ずつ。**規約の書き換えは承認の後**。この skill の仕事は提案まで。
5. 記録する。hub の `docs/notes/retro-YYYY-MM-DD.md` に、所見（3 分類）・反映案・数値を書く。数値は
   `braindex retro stats -window-days 14 -by project,week,position` の表をそのまま貼る（本文は貼らない）。
   ダイジェスト本体は残さない（一時ディレクトリに置いたままにし、OS の掃除に任せる）。
6. `braindex` で索引を再生成し、ノートと一緒にコミットする。

閾値と窓は `braindex.json` の `retro` 節（`threshold`・`window_days`）。辞書は `dictionary`（既定辞書の差し替え）と `dictionary_extra`（追加）で、
1 行 1 正規表現のファイルを指す。所見で「辞書が拾えなかった訂正の定型句」が見つかったら、`dictionary_extra` に足す案も反映案に含める。
位置別（`-by position`）の率がセッションの後半ほど高ければ、「長いセッションでは新しいセッションを勧める」目安（何発話目か）も反映案に含める。
