# braindex — 索引の生成

[← README](../README.md) ／ [手引きの目次](README.md)

索引はコピーではなくパスを持つ。生成・参照・レビューはこう回る。

```text
生成:  各リポの docs/notes/**/*.md ＋ docs/decisions.md
         └─▶ scan（走査）─▶ extract（日付・種別・タイトル・要旨）─▶ render（1 行に整形）
               └─▶ hub の index/catalog.md（LF 固定。同じ入力なら常にバイト一致）
               └─▶ hub の index/changes.json（本文のハッシュと観測日。索引の行が変わらない本文だけの更新を見分ける）

引く:  人 / エージェント ─▶ catalog.md を grep ─▶ ヒット行のパスの実ファイルを読む
         索引はコピーを持たない。要旨 80 字は手がかりであって、内容の代わりではない

回す:  catalog.md をコミット ─▶ 再生成すると git diff ＝ 前回からの差分
         └─▶ braindex review が索引の増減・差分ファイル・放置 TODO を集計し、週次レビューの下書きへ
```

## 索引が最新かを確認する `-check`

`braindex -check` はいつもどおり索引を生成し、保存済みの `index/catalog.md` と比べる。
生成日の行は比較から除く。終了コードは **0 最新／3 古い／1 失敗**。差分がなくても走査に警告があれば 2 を返す。
保存済みの索引が無い、または読めない場合は 1。`-config`・`-root`・`-out` は通常の生成と同じように指定できる。
古い場合は、行の追加・削除・置換の最小回数を「差分 N 行」と 1 行で表示する。
`catalog.md`・`changes.json` を含め、ファイルは一切書かない。
比較対象は索引の内容なので、要旨など索引の行に表れない本文だけの変更は検出しない。

## 設定 `braindex.json`

`braindex.json`（カレントディレクトリ。`-config` で変更可。無くてもよく、そのときは `-root` が必須）:

| キー | 意味 |
|---|---|
| `root` | 走査のルート。直下の各ディレクトリを 1 リポとみなす（`repo_depth` で段数を変えられる）。相対パスは設定ファイルのディレクトリ基準。`-root` が無ければ必須 |
| `repo_depth` | root から何段下のディレクトリをリポとみなすか。既定 1（root 直下）。`2` なら `root/<group>/<name>` がリポで、リポ名（索引の H2 見出し・`extra.repo`・`search -repo` など）は `group/name`。段数は root 全体で 1 つ（1 段と 2 段の配置は混ぜられない。2 段のときは 1 段目の `docs/notes` は見ない）。0 または省略で 1、負の値は設定の誤り。列挙できなかった group は「読めなかった範囲」として索引の先頭に残る |
| `notes_dirs` | 各リポのノート置き場。既定 `["docs/notes"]`。`["wiki"]` や、移行中の `["docs/notes", "wiki"]` も可。種別ラベルは末尾セグメント。リポ内の相対パスに限る（`..` を含むパスと絶対パスは設定の誤りとして終了コード 1） |
| `extra` | 規約外の置き場を個別に足す配列。各要素は `repo`（リポ名。`repo_depth` が 2 なら `group/name`）・`path`（リポ内の起点。`"."` はリポ直下。`notes_dirs` と同じくリポ内の相対パスに限る）・`recursive`（`true` でサブディレクトリも走査）・`kind`（種別ラベル）・`exclude`（グロブの配列。`/` を含むパターンは起点からの相対パス、含まなければファイル名とディレクトリ名に掛ける。ディレクトリに当たるとその枝ごと除外する。大文字小文字は区別する） |
| `review` | 週次レビュー（`braindex review`・[review-lint.md](review-lint.md)）の節。`dir`（記録の置き場。既定 `work/review`）・`since_days`（前回の記録が無いときに遡る日数。既定 14）・`stale_todo_weeks`（TODO を放置とみなす週数。既定 4）・`archive_months`（何か月より前をアーカイブ候補にするか。既定 6）。省略可 |
| `retro` | 振り返り（`braindex retro`）の節。`sessions_dir`・`window_days`・`threshold`・`position_bins`・`dictionary`・`dictionary_extra`。省略可。詳細は [retro.md](retro.md) |
| `news` | ニュースサジェスト（`braindex news`・[news.md](news.md)）の節。`dir`（既定 `news`）・`feeds`（既定 `news/feeds.json`）・`seen_days`（既定 90）・`cap_per_layer`（層ごとの 1 フィード表示上限。既定 `{"daily": 15, "weekly": 25}`・表に無い層は 20）・`profile_days`（既定 14）・`sessions_dir`・`show_min_score`（主要表示にする関心度の下限。0〜3・既定 2。**0 は全件を主要表示**で、省略とは別の意味）・`llm`（`off`（既定）か `claude-cli`。LLM 補助の opt-in）・`llm_model`・`llm_timeout_sec`（既定 120）。省略可。範囲外の値は設定の誤りとしてエラー |
| `approvals` | 判断待ちのフォーム（`braindex approvals`・[tools.md](tools.md)）の節。`file`（既定 `work/APPROVALS.md`）・`decisions`（既定 `docs/decisions.md`）・`timeout_sec`（既定 0＝無期限）。省略可 |
| `schedule` | 定期実行（`braindex schedule`・[schedule.md](schedule.md)）の節。`jobs` の配列（`name`・`args`・`when`）。省略すると既定の 2 本。省略可 |

未知のキーはエラーにする（`notes_dir` のような打ち間違いを無言で無視しない）。

例（`alpha` リポの `research/` を種別 `research` で載せ、README と下書きを除く）:

```json
{
  "root": "..",
  "notes_dirs": ["docs/notes"],
  "extra": [
    { "repo": "alpha", "path": "research", "recursive": true, "kind": "research", "exclude": ["README.md", "*.draft.md"] }
  ]
}
```

例（`~/projects/<group>/<name>` のように 1 段はさんで整理している root。索引の見出しは `## work/alpha` になる）:

```json
{
  "root": "..",
  "repo_depth": 2,
  "extra": [
    { "repo": "work/alpha", "path": "research", "recursive": true, "kind": "research" }
  ]
}
```

フラグ: `-config` `-root` `-out`（既定は設定ファイルと同じディレクトリの `index/catalog.md`）`-date YYYY-MM-DD`（生成日の固定。テスト・CI 用）`-version`（入っている版を 1 行出して終わる）。
終了コード: 0 成功／1 失敗（フラグの誤り・設定・root が読めない。索引は書かない）／2 警告つき完了（読めないファイルや存在しない `extra` を stderr に出して飛ばし、索引は書く。本文の変更の記録を読めない・書けないときも同じ）。

## 索引の各行の決め方

- リポ: `root` の `repo_depth` 段下の各ディレクトリ（既定 1 で直下。どの段でも `.` で始まるものは除く）。リポ名は root 相対のスラッシュ区切り（`alpha`・2 段なら `work/alpha`）。root 相対パスに `archive` セグメントを含むファイルは除外
- 種別: ノート置き場の直下はその末尾セグメント（既定 `notes`）、サブディレクトリ配下は `notes/<サブディレクトリ>`、`docs/decisions.md` は `decisions`、`extra` は指定した `kind`（`recursive` ならサブディレクトリ配下は `kind/<サブディレクトリ>`）
- 日付: ファイル名の `YYYYMMDD` か `YYYY-MM-DD` → 本文先頭 10 行の ISO 日付か `YYYY年M月D日` → 無ければ空欄（mtime には頼らない）
- タイトル: 最初の `# ` 行。無ければファイル名（`.md` を除く）
- 要旨: タイトル直後の、見出し・表・コードフェンス・日付だけの行（`記録日:` `日付:` `更新日:` `作成日:` `Date:`）でない最初の本文行を 80 字で切る
- `decisions.md` だけ別扱い: 日付は全文の `記録日:` のうち最も新しいもの（追記式なので「最後に何か決めた日」）、タイトルは `<H1>（N 件）`、要旨は末尾の H2 見出し 1 件
- 並び: リポ名昇順 → 日付降順 → パス昇順。改行は LF 固定。入力の BOM と CRLF は正規化する

## 走査の記録（索引の先頭）

説明行の直後・最初のリポ見出しの前に、走査で読めなかった範囲の記録を置く。索引に行が無いことを「ノートが無い」と読む前に、ここを見る。

```text
走査: 読めなかった範囲なし
```

```text
走査: 読めなかった範囲 2 件（この範囲のノートは載っていない。無いのか読めないのかは分からない）
- 読めなかった: alpha/docs/notes/locked/ — permission denied
- 読めなかった: beta/docs/notes/x.md — permission denied
```

- 読めなかった範囲は、列挙できなかったディレクトリ（末尾 `/`）と、開けなかったファイル。パスは root 相対で昇順
- 表の行と `## ` 見出しだけを読む読み手はこの行を読み飛ばすので、表の形は変わらない（旧い読み手もそのまま使える）
- この記録を持たない索引（2026-09-06 より前の版で生成）は完全性が不明で、`braindex review` と `braindex diagnose` はそう扱う
- 終了コードは据え置き（読めない範囲は従来どおり警告して 2）。索引の生成を止めない——1 ファイルの権限エラーで索引全体を失わないため
- `braindex review` はこの記録を使い、前回にあって今回無い行を「削除」でなく「確認不能」（読めなかった範囲の中）と「対象外」（設定で見なくなった場所）に分ける（[review-lint.md](review-lint.md)）

## 本文の変更の記録 `index/changes.json`

索引の行は日付・種別・タイトル・要旨・パスだけなので、本文の後半だけを直した更新では行が変わらず、`git diff` にも出ない。
そこで生成のたびに、本文の内容ハッシュと「その内容を最初に見た日」を索引と同じディレクトリの `changes.json` に書き、
次の生成でハッシュが違えば「本文が変わった」と分かるようにする。索引の日付（記録日）は変えない——いつ書いた知識か
という情報を失わないため。mtime は使わない（git が保存しないので clone ごとに変わる）。

```json
{
  "version": 1,
  "notes": [
    { "path": "alpha/docs/notes/a.md", "hash": "<sha256>" },
    { "path": "alpha/docs/notes/b.md", "hash": "<sha256>", "observed": "2026-09-07" },
    { "path": "beta/docs/notes/old.md", "hash": "<sha256>", "observed": "2026-08-01", "missing": "2026-09-01" }
  ]
}
```

- `hash`: BOM を除き、CRLF・CR を LF に揃えた本文の SHA-256（16 進）。checkout の改行変換や BOM の付け外しは変更に数えない。
  内容が変わったことを見分ける値であって、意味のある変更かどうかは判定しない
- `observed`: その内容を braindex が最初に見た日（生成日。`-date` で固定できる）。無いのは「記録を始めた時点で既にあった」＝
  いつ変わったかは不明。初回の生成では全件が観測日なしになり、「今日変わった」とは記録しない
- `missing`: 走査で見当たらなくなった日。同じ内容で戻れば消え、`observed` は元のまま。違う内容で戻れば `observed` が戻った日になる
- 読めなかった範囲（索引先頭の「走査:」の行）にある記録は前回のまま据え置く。読めなかっただけで、消えたとも変わったとも言わない
- 並びは `path` 昇順・LF・インデント 2。同じ材料と同じ生成日からは同じバイト列になるので、`catalog.md` と一緒にコミットしてよい
  （記録日は動かないまま、本文の変更が diff に出る）
- 壊れていて読めない（手で編集した・別の版が書いた）ときは、警告して記録を触らず索引だけ書く（終了コード 2）。
  直すか、ファイルごと消せば次の生成が初回として観測をやり直す
- 書けなかったときも警告にとどめる（索引は書けている。観測は次の生成で追いつく）。同じ hub で生成が重なると、Windows では
  置き換えの瞬間に片方が拒まれてこの警告になることがある。記録が半端な内容になることはない
- stdout の 1 行: 初回は `本文の観測を開始: N 件を記録(いつ変わったかは不明)`、以後は `本文の変更: 変更 a・新規 b・見当たらない c`
  （再出現があれば `・再出現 d`、据え置きがあれば `(読めなかった範囲の e 件は前回のまま)`）か `本文の変更: なし`

関心プロファイル（`braindex news profile`・`news fetch` の採点・`learn` の材料）はこの記録を読み、記録日が古くても `observed` が窓の中にあるノートを数える（材料の行に「うち N は本文の変更で数えた」と出る）。記録が壊れていれば警告して（終了コード 2）、本文だけの変更は数えずに残りで作る。

## 決めたこと

記録日・理由・根拠は `docs/decisions.md` にあった当時の記録のまま。

### 読めないものは警告して飛ばし、索引は書いて終了コード 2。失敗（root・設定・フラグの誤り）は 1 で索引は書かない

記録日: 2026-09-02
理由: 無言スキップは索引の欠けに気づけない。一方で 1 ファイルの権限エラーで索引全体を止めるのも過剰なので、飛ばした対象を stderr に列挙したうえで索引は書き、終了コードで「完了したが欠けがある」を伝える。ノート置き場を持たないリポは正常なので警告しない。フラグの誤り・位置引数は flag パッケージ既定の 2 でなく 1 にする（2 を「警告つき完了」と取り違えないため。PR #2 レビュー指摘）。
根拠: 会話 2026-09-02（PR #2（控え: pr/2.md） とそのレビュー。実測: `braindex -bogus` が exit 2 を返し、警告つき完了と区別できなかった）。実装は `cmd/braindex/main.go` のパッケージコメント

### パスの基準: 設定ファイル内の相対パスは設定ファイルのディレクトリ、フラグの相対パスはカレント。root に既定値は無い

記録日: 2026-09-02
理由: 原型は root の既定を `".."`（hub の親）に固定していて、hub 以外の場所から実行すると別のディレクトリを走査した。設定ファイルの隣に置くものは設定ファイル基準（どこから実行しても同じ結果）、コマンドラインで渡すものはシェルの慣習どおりカレント基準にする。root は環境ごとに違うので既定を置かず、無ければ「設定ファイルの有無」を添えてエラーにする。優先順位はフラグ > 設定 > 既定値。
根拠: 会話 2026-09-02（PR #2（控え: pr/2.md））。原型の `main.go` / `scan.go` にあった `".."` 固定は同 PR で削除

### `extra` の `exclude` はグロブ（`path.Match`）にし、`/` を含むパターンは起点からの相対パスに掛ける

記録日: 2026-09-02
理由: ワイルドカード無しは従来どおり完全一致なので既存の設定は変わらない。不正なパターンは設定の誤りなので `Scan` の入口でエラーにし、無言で文字列比較に落とさない（PR #3 のコミットメッセージより）。グロブ化そのものの動機は PR 本文に書かれていない（推測: `*.draft.md` のような一群を 1 件ずつ列挙しないため）。`*` は `/` を跨がないので `sub/*` は `sub/` 直下だけを除外し、サブツリー全体の除外は未対応（要判断 → `work/APPROVALS.md` 1・2026-09-02 に積んだ）。※ この最後の一文は 2026-09-03 の決定「`exclude` のパターンをディレクトリにも掛け、当たった枝を丸ごと除外する」で上書きした。以後 `exclude` はディレクトリにも掛かるので `sub/*` も `sub` も枝ごと除外し、「直下だけ」は書き表せない。
根拠: PR #3（控え: pr/3.md） https://github.com/pilefort/braindex/pull/3（2026-09-02 ユーザー LGTM）／実測（2026-09-02・Windows: `sub/*` で `sub/deep/e.md` が残る）は `docs/notes/project/review-evidence-2026-09.md`「`exclude` のグロブは `/` を跨がない」に写した（出典の当時のレビュー記録は git 管理外・現存せず）

### 日付が取れないノートは日付を空欄にし、mtime にも `git log` にもフォールバックしない

記録日: 2026-09-02
理由: git は mtime を保存しないので、mtime に頼ると clone ごとに索引が変わり、決定性（同一入力で 2 回生成してバイト一致）が壊れる。空欄は「日付を書いていない」事実をそのまま見せ、規約（日付を入れる）へ戻す圧にもなる。日付なしの行は同じリポの中で日付のある行の後ろに並ぶ。却下案: `git log` の日付は、コミット済みの内容には決定的だが未コミットのノートには効かず、ファイルごとに外部プロセスを起動する依存が増えるため却下。
根拠: PR #4（控え: pr/4.md） https://github.com/pilefort/braindex/pull/4（本文「`git log` の日付を採らなかった理由」）／`internal/catalog/catalog_test.go` の `TestBuild_DeterministicAcrossMtime`（mtime だけ違う 2 ツリーでバイト一致。2026-09-02 のレビューで mtime フォールバックを戻すと `~2020-01-01` の行が出て落ちることを実測 → `docs/notes/project/review-evidence-2026-09.md`「日付を mtime にフォールバックすると決定性テストが落ちる」。出典の当時のレビュー記録は git 管理外・現存せず）

### `exclude` のパターンをディレクトリにも掛け、当たった枝を丸ごと除外するか → A. ディレクトリ名にもパターンを掛け、当たったら `SkipDir` で枝ごと落とす（gitignore と同じ感覚。`/` 無しのパターンはディレクトリ名にも掛かる）

記録日: 2026-09-03
理由: 利点: `drafts/*` と書いた意図どおり動く／欠点: マージ済み PR #3 の意味を変える。実装・テスト・README の 1 行を足す小 PR が 1 本要る（選択肢の記載どおり・ユーザー補足なし）。却下: B. 現状のまま、「`*` は `/` を跨がない。サブツリーの除外は不可」を README に明記する
根拠: 会話 2026-09-03（ユーザー判断・承認待ち HTML の回答）。選択肢と得失は当時の `work/APPROVALS.md`（このリポでは git 管理外。却下案は理由行に転記済み）

### 索引の要旨は日付だけの行（`記録日:` など）を飛ばす

記録日: 2026-09-06
理由: 「結論を先頭に・日付を入れる」規約に素直に従うと、H1 の次の行が `記録日: 2026-09-06` になる。旧規則はそれを最初の本文行として拾うので、索引の要旨が日付だけになってノートの中身が分からなかった。飛ばす対象は `記録日` `日付` `更新日` `作成日` `Date` で始まりコロンが続く行に限る（本文中に日付を含む文は要旨として有効なので、行頭のラベルだけを見る）。
根拠: 設計レビュー 2026-09-06 M6（`docs/notes/project/design-review-2026-09-06.md`）／実装は `internal/extract/extract.go` の `dateLineRe`、判定は `TestExtract_Summary` の「日付行は要旨にしない」（PR `review/m4-m6-extract`）

### root を 2 段にするには `repo_depth`（既定 1）を足す。複数 root（`roots: []`）は採らない

記録日: 2026-09-06
理由: `repo_depth: 2` なら `group/name` をリポ名にするだけで、パスが root 相対のまま一意という今の性質が壊れない（索引の H2 見出しが `work/alpha` になる）。却下: `roots: []` で複数の root を並べる案——パスの基準が root ごとに変わるので「root 相対パス」の意味が 1 つに定まらず、`-root` フラグとの関係も決め直しになる。`repo_depth` は深さが全体で 1 つなので 1 段と 2 段が混ざる root には合わないが、その要求が実際に出てから考える。実装に入る前に決めたのは、後から変えると索引の見出しが変わって差分が全件になるため。
根拠: 会話 2026-09-06（ユーザー判断・承認フォームの回答）／設計レビュー 2026-09-06 M5（`docs/notes/project/design-review-2026-09-06.md`）／影響範囲は `internal/scan`・`extra.repo` の検査・`review/todo.go` と `cmd_lint.go` のリポ列挙

### 索引は走査で読めなかった範囲を先頭に記録し、週次レビューはその範囲の行を「削除」でなく「確認不能」、今の設定が見に行かない場所の行を「対象外」にする

記録日: 2026-09-06
理由: 索引に行が無いことは「ノートが無い」証明にならない。権限エラーなどでディレクトリを列挙できない・ファイルを読めないと、その範囲のノートは索引から抜けるが、週次レビューの差分はそれを「削除」と数えていた（増減が嘘をつく）。そこで、走査は読めなかった範囲を構造化して返し（`scan.Result.Gaps`）、索引はそれを先頭の「走査:」行に残す（この記録を持たない旧い索引は「完全性不明」として区別する）。差分は、削除と断定する前に「確認不能」（読めなかった範囲の中）と「対象外」（設定を変えた・archive へ移した）へ振り分ける。索引の表の形は変えないので、表の行だけを読む旧い読み手はこの記録を読み飛ばせる。終了コードは据え置く（読めない範囲は従来どおり警告して 2）。却下: 読めない範囲があれば索引を書かない（1 ファイルの権限エラーで索引全体を止めるのは過剰。2026-09-02 の決定を維持）／記録を別ファイル（JSON）に持つ（正本が 2 つになる。設計レビュー補足の「JSON の別ファイルは独立した正本にしない」に反する）。
根拠: 設計レビュー補足 2026-09-06「部分的な索引を完全な調査結果として扱わない」（`docs/notes/project/design-review-addendum-2026-09-06.md`）／振り分けは `internal/review/index.go` の `diffEntries`、記録の形式は `internal/catalog/coverage.go`、走査は `internal/scan/scan.go` の `Result`・`Gap`・`Covers`（PR `codex/dr-scan-coverage`）／Windows で「見つかるが読めない」状態は排他オープン（共有を許さずに開いたままにする）で再現できる（2026-09-06 実測: `ReadFile`・`ReadDir` が共有違反で失敗し、`filepath.WalkDir` は 2 回目の呼び出しでエラーを渡す。道具は `internal/scan/scantest`）

### 本文の変更は索引に入れず、索引と同じディレクトリの `changes.json` に内容ハッシュと観測日で記録する。記録日は変えず、初回は観測日を不明にする

記録日: 2026-09-06
理由: 索引の行は日付・種別・タイトル・要旨・パスだけなので、本文の後半だけを直した更新では行が変わらず、関心抽出の「索引の直近差分」にも載らない。本文のハッシュ（BOM 除去・LF 正規化後の SHA-256）を持てば内容の変化は見分けられるが、「いつ変わったか」は生成した日で決まるので、同じ入力から常にバイト一致であるべき索引には入れられない。そこで索引と同じディレクトリの `changes.json` に、パス・ハッシュ・その内容を最初に見た日（観測日）を持つ。索引の日付（記録日）を更新日に置き換えないのは、いつ書いた知識かという情報を失うため。記録が無い初回は観測日を空（不明）にする——全件を「今日変わった」と記録すると、関心抽出が初回の直後に全ノートを最近の変更として数えてしまう。読めなかった範囲にある記録は前回のまま据え置く（読めなかっただけで、消えたとも変わったとも言えない）。壊れた記録は警告して触らない（黙って作り直すと前回の観測を失う）。却下: 索引の表にハッシュの列を足す（表の読み手は 5 列を前提にしているので旧い索引も読み手も全部変えることになる。索引の diff に 64 桁のハッシュも並ぶ）／mtime を使う（決定 2026-09-02 のとおり git が保存しない）／排他ロックを入れる（生成が重なっても書き切ってから置き換えるので記録は壊れず、片方が警告で終わるだけ。複数ファイルにまたがる復旧はニュースの中断復旧の担当が設計する）。
根拠: 設計レビュー補足 2026-09-06「ノートの日付と、内容が変わった時点を分ける」（`docs/notes/project/design-review-addendum-2026-09-06.md`）／実装は `internal/changehistory`（規則は `Update`、書式は `Marshal`・`Parse`）、生成側は `cmd/braindex/main.go`、関心抽出の口は `internal/interest` の `Input.Changes`（PR `codex/dr-content-changes`）／本文だけの変更で索引がバイト一致のままハッシュだけ変わることは `internal/catalog/notes_test.go`、初回・読めない範囲・削除と再出現・壊れた記録・同時実行は `internal/changehistory/changehistory_test.go` と `cmd/braindex/main_changes_test.go`／Windows で生成が重なると置き換えが「Access is denied」で拒まれることがある（2026-09-06 実測: 同時実行テストを 20 回回した範囲で拒まれた回があり、記録は毎回完全だった）

### `repo_depth` はテンプレの `braindex.json` に足さず、使う人が手で書く。リポの列挙は `scan.ListRepos` の 1 か所にする

記録日: 2026-09-06
理由: テンプレに `"repo_depth": 1` を置くと、`update` が既存の全 hub にその行を足し、古い版のバイナリがその hub を未知のキーで読めなくなる（決定 2026-09-06「未知の節はエラーのまま」）。既定と同じ値を配って得るものが無いのに、版ズレの実害だけが増える。2 段の配置を使う人だけが `repo_depth: 2` を書けばよい。リポの列挙は索引（`scan`）・週次レビューの放置 TODO（`review/todo.go`）・`lint` で三重に書かれていたので、`scan.ListRepos` に一本化した——段数の規則を変えるとき、直す場所は 1 か所で済む。列挙できなかった group は「読めなかった範囲」（`Gap`）として返し、配下にリポが無いとはみなさない（決定 2026-09-06「索引は走査で読めなかった範囲を先頭に記録」と同じ扱い）。却下: テンプレに足して `internal/template` の固定キー順にも登録する案（上記の版ズレに加え、機能 `core` の節が増えて `update` の差分が全 hub に出る）／`review`・`lint` に段数だけ渡して各自で列挙する案（三重定義が残る）。
根拠: 決定 2026-09-06「root を 2 段にするには `repo_depth`（既定 1）を足す」の実装（PR `review/m5-repo-depth`）／テンプレの節は `internal/template/feature.go` の `Sections` と `config.go` の `configKeyOrder` に登録しないと `TestFeatures_CoverAllConfigSections` が落ちる（実装時に確認）／列挙の共用は `internal/scan/scan.go` の `ListRepos`、既定で出力が変わらないことは `internal/scan/depth_test.go` の `TestScan_DefaultDepthIsOne`、2 段の索引の決定性は `internal/catalog/catalog_test.go` の `TestBuild_E2EGolden_RepoDepth2`
